# Порядок работы с проектом

Документ задаёт соглашение команды для дальнейших изменений. Он не утверждает, что каждый исторический коммит прошёл одинаковый процесс.

## Изменение от задачи до проверки

1. Описать проблему, ожидаемый результат и критерий приёмки в задаче соответствующего репозитория.
2. Указать ответственного, зависимости между клиентом/API/данными и объём документации.
3. Создать короткую рабочую ветку от актуального `main`: `feature/...`, `fix/...`, `docs/...` или `refactor/...`.
4. Внести изменение и выполнить подходящие проверки. Для документации проверить ссылки, соответствие коду и отрисовку схем; для поведения — соответствующие тесты и пользовательский путь.
5. Открыть Pull Request в `main` с описанием результата, способов проверки и существенных ограничений.
6. Получить review другого участника и проверить CI там, где он настроен. После объединения актуализировать связанную задачу и документы.

`main` — основная ветка текущего приложения. Существующие ранние ветки могут оставаться в истории; новая работа не требует перехода через них.

## Готовность задачи к работе

Понятны пользователь/эксплуатационная цель, текущее и желаемое поведение, границы, критерии приёмки и необходимые зависимости. Неизвестные решения явно обозначены; сроки не подменяют описание результата.

## Готовность результата

- Реализовано согласованное поведение, включая ошибки и права доступа.
- Проверки соответствуют изменению; skipped-сценарии не названы выполненными.
- README, требования, API и схемы обновлены там, где затронут контракт.
- В репозитории нет рабочих баз, чужих фотографий, токенов, паролей среды и локальных весов модели.
- Review и CI оценены по конкретному commit SHA.

## Коммиты и Pull Request

Рекомендуемый формат коммита: `feat: ...`, `fix: ...`, `docs: ...`, `refactor: ...`, `test: ...`, `chore: ...`. Название должно описывать итог, а не «финальную версию» или номер попытки.

В PR сначала объясняются проблема и новое поведение. Далее — необходимые технические детали и проверки. Не следует переносить в описание весь разговор, старые варианты решения или утверждения о проверках без подтверждения.

## Актуальность документов

Распределение материалов и правила обновления — в [BASELINE](../BASELINE.md). Требования описывают наблюдаемое поведение, архитектура — устройство, RUNBOOK — воспроизводимые действия, roadmap — ещё не выполненные работы. История Git сохраняет прежние редакции; противоречивые копии не нужны в текущей навигации.
