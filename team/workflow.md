# Nexus — Workflow и стандарты разработки

**Workflow команды Nexus** — регламент управления задачами, версионирования кода, стандарты коммитов и процесс Code Review для обеспечения качества и синхронизации работы команды.

Этот документ описывает процессы разработки, принципы работы с Git, критерии готовности задач (DoR / DoD), соглашения по коммитам и пошаговый алгоритм выполнения задач.

---

## 🌳 Git-стратегия и ветки

### Основные ветки
- **`main`** — стабильное состояние, готовое к продакшену
- **`develop`** — интеграционная ветка для ведения разработки

### Рабочие ветки
```
feature/<name>      # Новые функции
bugfix/<name>       # Исправление ошибок
docs/<name>         # Обновление документации
refactor/<name>     # Рефакторинг кода
```

### Примеры именования
```
feature/user-auth
feature/recommendations
feature/chat
bugfix/duplicate-likes
docs/business-requirements
refactor/recommendation-service
```

## 📋 Жизненный цикл задачи

### Этапы выполнения

| Шаг | Действие | Описание |
|-----|----------|---------|
| 1️⃣ | Создать Issue | Описать задачу в репозитории |
| 2️⃣ | Указать метаданные | Тип, область, приоритет |
| 3️⃣ | Добавить в Project | Поместить в GitHub Project Board |
| 4️⃣ | Назначить ответственного | Указать исполнителя |
| 5️⃣ | Создать ветку | Новую рабочую ветку от `develop` |
| 6️⃣ | Разработка | Осмысленные коммиты с соблюдением convention |
| 7️⃣ | Pull Request | Создать PR в `develop` |
| 8️⃣ | Связать с Issue | Упомянуть Issue в описании PR |
| 9️⃣ | Code Review | Провести рецензию кода |
| 🔟 | Merge & Done | Слить PR и переместить задачу в Done |

## ✅ Definition of Ready (DoR)

Задачу можно брать в работу, если выполнены все пункты:

- ✔️ **Цель понятна** — четко определено, что нужно сделать
- ✔️ **Ожидаемый результат указан** — описан желаемый результат
- ✔️ **Зависимости определены** — известны связи с другими задачами
- ✔️ **Критерии приёмки описаны** — как проверить, что задача выполнена

---

## 🎯 Definition of Done (DoD)

Задача считается завершённой при соблюдении всех условий:

- ✔️ **Код или документация добавлены** — все изменения реализованы
- ✔️ **Локальная проверка** — протестировано на локальной машине
- ✔️ **Отсутствуют очевидные ошибки** — базовая валидация пройдена
- ✔️ **PR прошёл review** — одобрено как минимум одним рецензентом
- ✔️ **Документация актуальна** — обновлены README / Swagger / docs при необходимости
- ✔️ **Issue закрыт** — задача перемещена в Done и связана с merged PR

## 📝 Соглашение по коммитам (Commit Convention)

### Формат

```
<type>: <short description>
```

### Типы коммитов

| Тип | Назначение | Пример |
|-----|-----------|--------|
| `feat` | Новая функция | `feat: add user registration endpoint` |
| `fix` | Исправление ошибки | `fix: prevent duplicate likes` |
| `docs` | Обновление документации | `docs: describe business requirements` |
| `refactor` | Рефакторинг без изменения функций | `refactor: split recommendation service` |
| `test` | Добавление или обновление тестов | `test: add auth endpoint tests` |
| `chore` | Изменения конфигурации, зависимостей | `chore: update dependencies` |
| `style` | Форматирование кода | `style: fix linting errors` |

### Рекомендации

- Используйте **imperative mood** (повелительное наклонение): "add", "fix", "update" (не "added", "fixed", "updated")
- Описание — **строчная буква** в начале
- Длина описания — **максимум 50 символов**
- Используйте детальное описание в теле коммита для сложных изменений

### Примеры хороших коммитов

```
feat: add user registration endpoint
fix: prevent duplicate likes
docs: describe business requirements
refactor: split recommendation service
test: add authorization middleware tests
```

## 👥 Code Review Процесс

### Чеклист рецензента

- 📖 Описание PR понятно и связано с Issue
- ✅ Код соответствует стилю и соглашениям проекта
- 🧪 Логика верна и нет очевидных ошибок
- 📚 Новые функции задокументированы
- 🔐 Нет проблем безопасности или утечек данных
- ⚡ Производительность не деградировала
- 📝 Коммиты осмысленные и следуют convention
- ✔️ Локально протестировано

### Правила слияния

- ✅ Минимум **1 одобрение** (approve)
- ✅ **Все checks** (CI/CD, линтер, тесты) должны быть green
- ✅ Ветка должна быть **в синхронизации** с `develop`
- ✅ **Squash or rebase merge** (по соглашению команды)
