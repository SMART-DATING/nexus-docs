# Смысловой подбор

Подбор использует сохранённые личные рассказы, а не анализ фотографий и не совпадение публичных тегов. Модель работает локально на сервере. Это способ упорядочить анкеты по близости текстов, а не психологическая оценка людей.

## Модель и представление текста

Используется готовая RuBERT-tiny2, экспортированная в ONNX; выходной вектор содержит 312 измерений. Модель не дообучается на пользователях и реакциях. Точная ревизия, лицензия, контрольные суммы и команды загрузки зафиксированы в [backend MODEL.md](https://github.com/SMART-DATING/nexus-backend/blob/main/MODEL.md).

`SemanticEncoder` выполняет WordPiece-токенизацию с сохранением регистра. Длинный текст разбивается на блоки до 254 содержательных токенов плюс CLS/SEP. Из каждого берётся CLS-вектор и нормализуется. Блоки объединяются с весом числа токенов, результат снова нормализуется. Поэтому хвост длинного рассказа не отбрасывается.

`ContextService` сохраняет вектор каждой истории и версию алгоритма. Вектор участника — нормализованная сумма векторов всех его историй, то есть равный вклад отдельных рассказов. Название истории в расчёте не участвует. При иной сохранённой версии вектор пересчитывается; при обычном перелистывании текущие векторы читаются из БД без повторного inference.

Для нормализованных векторов `u` и `v`:

```text
score(u, v) = sum(u[i] * v[i]), с ограничением результата диапазоном [-1, 1]
процент в UI = round(max(0, score) * 100)
```

## Допуск и порядок анкет

1. Нужны четыре свойства собственного профиля и собственный рассказ. UI дополнительно требует хотя бы одно фото.
2. Исключаются сам пользователь, уже получившие его Like/Skip, заблокированные в любой стороне, скрытые, неполные и не имеющие рассказа кандидаты.
3. Возраст кандидата проверяется по диапазону смотрящего. Пол должен соответствовать выбору обоих участников. Встречный возрастной диапазон сейчас не проверяется.
4. Кандидаты из того же города ставятся перед остальными. Для сравнения удаляются внешние и повторяющиеся пробелы, регистр и различие `ё/е` не учитываются. Это не поиск расстояния или геокодирование.
5. Внутри каждой группы — score по убыванию, затем userId по возрастанию. Город и теги не меняют значение score.
6. Порог сходства отсутствует. Низкие, нулевые и отрицательные значения остаются в очереди, если остальные правила выполнены.

`remainingCount` сообщает число оставшихся подходящих кандидатов от текущей позиции всей очереди, а не размер одного ответа. `similarityFloor` — оставшееся поле совместимости; оно не фильтрует выдачу и не показывается как порог в интерфейсе.

Когда новых кандидатов не осталось, `POST /recommendations/next` может удалить собственные Skip и открыть новый круг. Like, match, сообщения и чужие реакции сохраняются. Обычный GET выдачи не сбрасывает реакции.

## Небольшой пример

У смотрящего город Москва. Для подходящих кандидатов рассчитаны:

| Кандидат | Город | Score | Позиция |
| --- | --- | --- | --- |
| А | Москва | 0.42 | 1 |
| Б | Москва | 0.18 | 2 |
| В | Казань | 0.81 | 3 |
| Г | Пермь | 0.00 | 4 |

Высокое сходство из другого города не обгоняет свой город; нулевое не исключается. Проценты остаются 42, 18, 81 и 0 — город не добавляет к ним баллы.

## Качество и ограничения

`SemanticEncoderTest` проверяет токенизацию, размер/норму вектора, несколько русских парафраз и влияние текста после первого блока. Детерминированные API-тесты отдельно проверяют порядок городов, проценты, фильтры и повтор пропусков. Эти проверки не устанавливают качество знакомств на реальной аудитории.

Короткие, неоднозначные или повторяющиеся тексты могут давать слабый сигнал. Нет обучения на выборе людей, автоматического объяснения общих ценностей, визуальных предпочтений и внешнего векторного индекса. Реальный эффект следует оценивать пользовательским исследованием по [бизнес-требованиям](../requirements/business-requirements.md).

При отсутствии файлов модели приложение может отвечать на health и другие API, но сохранение рассказа возвращает 503. Повреждённая установленная модель может остановить запуск. [Диагностика](../RUNBOOK.md).
