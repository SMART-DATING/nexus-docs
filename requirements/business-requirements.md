# Nexus — Бизнес-требования и анализ

**Бизнес-требования (Business Requirements)** — описание того, **зачем** создаётся система, какие проблемы она решает, каков контекст рынка, и какие показатели успеха определяют её эффективность. Это верхний уровень, от которого спускаются функциональные и нефункциональные требования.

---

## 📍 Контекст задачи

### Проблема, которую решает Nexus

**Текущее состояние:**
- 😕 Люди тратят много времени на поиск новых знакомств и собеседников
- 😕 Обычные социальные сервисы требуют самостоятельно искать пользователей
- 😕 Приходится фильтровать большое количество профилей вручную
- 😕 Часто опираются на поверхностные признаки (фото, базовая информация)
- 😕 Сложно оценить реальную совместимость по интересам и ценностям

**Решение Nexus:**
- ✅ **Персонализированный подбор** на основе анализа профилей и интересов
- ✅ **Экономия времени** — система сама предлагает релевантных людей
- ✅ **Взаимная заинтересованность** — общение начинается только при взаимном Like
- ✅ **Безопасность** — встроенный чат после Match, контроль доступа
- ✅ **История взаимодействий** — система учится и улучшает рекомендации

## 🎯 Бизнес-цель проекта

**Основная цель:**

> Создать веб-сервис, который помогает пользователям **находить людей с похожими интересами** и **начинать безопасное общение** после взаимного выражения интереса.

**Стратегическое видение:**
- Сократить время поиска релевантных контактов с часов до минут
- Повысить качество рекомендаций за счёт учёта интересов и истории
- Обеспечить безопасное и контролируемое общение
- Создать расширяемую платформу для будущего развития

## 📋 Основные бизнес-требования

### BR-01. 🔐 Регистрация и управление учётной записью

**Описание:**  
Система должна позволять человеку **создать учётную запись** с электронной почтой и паролем, получив доступ к персонализированным функциям.

**Обоснование:**
- Каждый пользователь должен иметь уникальную идентичность
- Защита данных требует аутентификации
- Основа для всех персонализированных функций

**Связь с FR:** FR-AUTH-01, FR-AUTH-02, FR-AUTH-03

**Метрики:**
- ✅ Успешная регистрация пользователя
- ✅ Отсутствие дублей аккаунтов
- ✅ Безопасное хранение паролей (BCrypt)

---

### BR-02. 👤 Формирование и управление профилем

**Описание:**  
Пользователь должен иметь возможность **описать себя**, указать **интересы** и **предпочтения**, которые влияют на рекомендации и видимость профиля.

**Компоненты профиля:**
| Компонент | Назначение | Обязателен |
|-----------|-----------|-----------|
| Основная информация | Имя, возраст, город, фото | ✅ Да |
| Описание (Bio) | Рассказ о себе (500-1000 символов) | 🟡 Желательно |
| Интересы | Выбор из справочника (min 1) | ✅ Да |
| Предпочтения | Параметры поиска (возраст, расстояние) | ✅ Да |
| Фотографии | До 5 фото профиля | 🟡 Желательно |

**Почему это важно:**
- Полный профиль → лучшие рекомендации
- Интересы — основа алгоритма совместимости
- Предпочтения → фильтрация релевантных кандидатов

**Связь с FR:** FR-PROFILE-01..04, FR-INTEREST-01..04, FR-PREF-01..02

---

### BR-03. 💡 Персонализированный подбор пользователей

**Описание:**  
Система должна **выдавать список потенциально интересных пользователей** на основе анализа профиля, интересов, предпочтений и истории. Не просто общий каталог, а **умные рекомендации**.

**Алгоритм рекомендаций:**
```
1. Получить профиль пользователя и его интересы
2. Исключить: самого пользователя, уже обработанные, неактивные профили
3. Для каждого кандидата:
   - Найти пересечение интересов
   - Рассчитать score совместимости
   - Проверить соответствие предпочтениям (возраст, расстояние)
4. Отсортировать по score
5. Вернуть топ-N рекомендаций
```

**Почему это бизнес-ценность:**
- 🎯 Пользователь получает релевантные рекомендации, а не случайные профили
- ⏱️ Экономия времени на поиск (часы → минуты)
- 📈 Повышается вероятность Match (если совместимость высокая)
- 🔄 Система может улучшать алгоритм со временем (ML в будущем)

**Связь с FR:** FR-REC-01..07

---

### BR-04. 👍 Выражение интереса к рекомендации

**Описание:**  
Пользователь должен иметь возможность **отметить другого пользователя как интересного (Like)** или **пропустить рекомендацию (Skip)**, сохраняя историю взаимодействий.

**Действия:**
- **Like** → "Этот профиль мне нравится"
- **Skip** → "Не интересует, показать другого"

**Бизнес-логика:**
- ✅ Каждый Like/Skip записывается в историю
- ✅ История учитывается при следующих рекомендациях
- ✅ Нельзя лайкнуть одного пользователя дважды
- ✅ Пропущенные профили больше не рекомендуются (пока)

**Почему это важно:**
- Система получает сигналы о предпочтениях пользователя
- История используется для улучшения алгоритма
- Контроль: пользователь сам выбирает, кого видеть

**Связь с FR:** FR-LIKE-01, FR-LIKE-02, FR-LIKE-03

---

### BR-05. 🔗 Взаимное совпадение (Match)

**Описание:**  
При **взаимном положительном интересе** (оба пользователя поставили Like друг другу) система должна **создавать Match**, который подтверждает взаимную заинтересованность.

**Сценарий:**
```
Пользователь A видит рекомендацию пользователя B
  ↓
User A нажимает Like
  ↓
System проверяет: есть ли Like от B к A?
  ↓
YES → Создаём Match (обоих участников уведомляем)
NO  → Просто сохраняем Like A
```

**Бизнес-правила Match:**
- ✅ Match создаётся **только при взаимности**
- ✅ Между одной парой может быть только **один** активный Match
- ✅ Match — это основание для общения в чате
- ✅ Оба участника получают **уведомление о новом Match**

**Почему это критично:**
- 🛡️ **Безопасность:** чат доступен только при взаимном согласии
- ✅ **Качество:** только заинтересованные люди начинают диалог
- 📊 **Метрика:** Match % показывает качество рекомендаций

**Связь с FR:** FR-MATCH-01, FR-MATCH-02, FR-MATCH-03

---

### BR-06. 💬 Общение после Match

**Описание:**  
**Пользователи с созданным Match** должны иметь возможность **обмениваться текстовыми сообщениями** в приватном чате.

**Ограничения:**
- ✅ Писать может **только участник Match**
- ✅ Чат видят **только участники** (приватный)
- ✅ История сообщений сохраняется
- ✅ Видна информация об отправителе (имя, фото)

**Почему чат только после Match:**
- 🚫 **Спам-профилактика:** предотвращает нежелательные сообщения
- 📌 **Сигнал интереса:** если есть чат → оба заинтересованы
- 🔒 **Приватность:** случайные люди не могут писать

**Связь с FR:** FR-MSG-01..05

---

### BR-07. 🔔 Уведомление о важных событиях

**Описание:**  
Система должна **информировать пользователя** о событиях, требующих внимания:
- 📌 Новое Match создано
- 💭 Получено новое сообщение

**Реализация уведомлений:**
| Событие | Кому | Когда отправить | Приоритет |
|---------|------|-----------------|-----------|
| New Match | Обоим участникам | Сразу после создания Match | 🔴 Высокий |
| New Message | Получателю | Сразу при отправке сообщения | 🔴 Высокий |

**Для MVP:** уведомления в UI приложения (позже можно добавить push, email)

**Почему это нужно:**
- ⏰ Пользователь узнаёт о новых возможностях общения
- 🎯 Повышает вовлечённость (engagement)
- 📱 Пользователь может проверить приложение и ответить

**Связь с FR:** FR-NOTIF-01..03

---

### BR-08. 🤖 Улучшение качества рекомендаций

**Описание:**  
**Рекомендации должны учитывать накопленные данные** о пользователе и его предыдущих взаимодействиях, постепенно становясь точнее.

**Факторы улучшения:**
1. **История Like/Skip** → система видит предпочтения
2. **Интересы пользователя** → основа совместимости
3. **Предпочтения (возраст, расстояние)** → фильтры
4. **Успешные Match** → какие рекомендации привели к результату (для аналитики)

**Дорожная карта:**
| Этап | Уровень | Реализация |
|------|---------|-----------|
| **MVP** | Базовый | Пересечение интересов + фильтры |
| **v1.1** | Средний | Вес интересов, история Like/Skip |
| **v2.0** | Продвинутый | ML embeddings, рекомендации похожих пользователей |

**Бизнес-ценность:**
- 📈 Чем больше интеракций → лучше рекомендации
- ✅ Повышение Match Rate (% взаимных лайков)
- 🎯 Сокращение времени до первого Match
- 💰 Готовность к монетизации (подписка на улучшенные рекомендации)

**Связь с FR:** FR-REC-05, FR-REC-06, FR-REC-07

---

### BR-09. 🔐 Безопасный доступ к данным

**Описание:**  
**Персональные данные и функции пользователя** не должны быть доступны посторонним без авторизации. Каждый пользователь видит только то, что ему разрешено.

**Принципы безопасности:**
| Принцип | Реализация | Пример |
|---------|-----------|--------|
| **Аутентификация** | JWT токены | Пользователь вводит email/пароль, получает токен |
| **Авторизация** | Проверка прав | User A не может читать сообщения User B (не в Match) |
| **Шифрование паролей** | BCrypt | Пароли хранятся как хеш, не как текст |
| **Приватность чатов** | Access Control | Сообщения видят только участники Match |
| **Пустые ошибки** | Не раскрывать info | Не писать "email не найден", а "Неверные учётные данные" |

**Требования безопасности:**
- ✅ Все защищённые API требуют JWT токен
- ✅ Сервер проверяет: "принадлежит ли ресурс текущему пользователю?"
- ✅ Пароли зашифрованы (BCrypt)
- ✅ Нет логирования паролей
- ✅ Ошибки не раскрывают информацию об аккаунтах

**Связь с FR:** FR-AUTH-04, FR-MSG-03, FR-ERR-04, NFR-03, NFR-04

**Описание:**  
**Архитектура должна позволять** в дальнейшем добавлять новые факторы совместимости, способы рекомендаций и новые пользовательские функции **без полного переписывания системы**.

**Примеры расширений (за пределами MVP):**
| Функция | Текущее состояние | Возможное расширение |
|---------|------------------|-------------------|
| Рекомендации | Пересечение интересов | ML embeddings, contextual ranking |
| Профиль | Текст + интересы | Верификация, видео, соц.сети |
| Общение | Текстовый чат | Видеозвонки, голосовые сообщения |
| Реакции | Like/Skip | Ratings, comments, shares |
| Уведомления | In-app | Push, email, SMS |

**Архитектурные решения для расширяемости:**
- ✅ **Слоистая архитектура** (Controller → Service → Repository)
- ✅ **Изолированный RecommendationService** (легко заменить алгоритм)
- ✅ **Нормализованная БД** (добавление новых интересов = одна SQL вставка)
- ✅ **REST API** (независимое развитие frontend/backend)
- ✅ **Документирование** (новые разработчики понимают структуру)

**Почему это важно:**
- 🚀 Быстрое добавление новых функций
- 💼 Возможность масштабирования (больше пользователей, новые рынки)
- 👥 Новые разработчики быстро входят в проект
- 📊 Возможность A/B тестирования алгоритмов

**Связь с FR:** Все модули (модульная, независимая реализация)

## ⚖️ Бизнес-правила (Business Rules)

Бизнес-правила — **неинвариантные ограничения** системы, которые **никогда не должны быть нарушены**, независимо от сценария использования.

### BRULE-01. Уникальность Email

**Правило:**  
Один email может принадлежать **только одной** учётной записи.

**Реализация:**
- ✅ На уровне БД: `UNIQUE (email)` на таблице users
- ✅ На уровне приложения: проверка перед регистрацией
- ✅ При попытке дубля: ошибка `EMAIL_ALREADY_EXISTS`

**Обоснование:** Без этого невозможно идентифицировать пользователя при входе.

---

### BRULE-02. Пользователь не рекомендуется самому себе

**Правило:**  
Пользователь **не должен видеть свой профиль** в рекомендациях.

**Реализация:**
```sql
SELECT * FROM users 
WHERE id != current_user_id  -- Исключить себя
  AND (другие условия)
```

**Обоснование:** Пользователь ищет новых людей, не самого себя. Технически невозможно создать Match с самим собой.

---

### BRULE-03. Защита от повторных Like

**Правило:**  
Повторный активный Like между **той же парой пользователей не создаётся**. Нельзя лайкнуть одного человека дважды.

**Реализация:**
- ✅ На уровне БД: `PRIMARY KEY (user_id, target_user_id)` на таблице likes
- ✅ На уровне приложения: проверка перед созданием

**Обоснование:** Один Like = одно мнение. Повторные лайки — это ошибка или попытка спама.

---

### BRULE-04. Match только при взаимности

**Правило:**  
Match создаётся **только если оба пользователя поставили Like друг другу**. Односторонний интерес — это просто Like, без Match.

**Сценарий:**
```
User A → Like → User B (Match не создан)
User B → Like → User A (ТЕПЕРЬ создаём Match)
```

**Обоснование:** Match — это **подтверждение взаимного интереса**. Защищает от нежелательных сообщений.

---

### BRULE-05. Общение только в Match

**Правило:**  
Отправка сообщений **разрешена только участникам существующего Match**. Нельзя писать случайному пользователю.

**Реализация:**
```java
// Проверка перед отправкой сообщения
if (!match.isParticipant(currentUserId)) {
    throw new ForbiddenException("No access to this match");
}
```

**Обоснование:** Спам-профилактика. Чат = доверие + взаимный интерес.

---

### BRULE-06. Удалённые профили не рекомендуются

**Правило:**  
Удалённый или деактивированный профиль **не участвует в новых рекомендациях** (но может оставаться в истории).

**Статусы профиля:**
```
ACTIVE          → Участвует в рекомендациях
INACTIVE        → Не видит рекомендации, но видит старые Match
DELETED         → Удалён из системы
BANNED          → Заблокирован администратором
```

**Обоснование:** Если пользователь удалил аккаунт, его не должны рекомендовать другим.

---

### BRULE-07. Интересы из справочника

**Правило:**  
Пользователь может выбирать интересы **только из предопределённого справочника**. Нельзя добавить произвольный интерес.

**Реализация:**
```sql
CREATE TABLE interests (
  id INT PRIMARY KEY,
  name VARCHAR(255) NOT NULL UNIQUE
);
```

**Обоснование:** Стандартизация. Все пользователи говорят на одном языке (один набор интересов).

---

### BRULE-08. Профиль влияет на рекомендации

**Правило:**  
**Изменение профиля может влиять** на последующие рекомендации. Если пользователь добавил новый интерес — он появится в критериях совместимости.

**Примеры:**
- Добавил "Travel" → появляются люди с Travel
- Изменил max_age с 30 на 35 → новые рекомендации

**Обоснование:** Профиль — это живой документ. Система должна реагировать на изменения.

---

### BRULE-09. История взаимодействий учитывается

**Правило:**  
История уже обработанных рекомендаций (Like/Skip) **должна учитываться**, чтобы **не показывать одного и того же пользователя бесконечно**.

**Реализация:**
```sql
-- Исключить уже обработанные
SELECT * FROM users 
WHERE id NOT IN (
  SELECT target_user_id FROM likes WHERE user_id = current_user_id
  UNION
  SELECT target_user_id FROM skips WHERE user_id = current_user_id
)
```

**Обоснование:** Без этого пользователь видел бы одних и тех же людей постоянно. История — это часть алгоритма.

---

### BRULE-10. Контроль над собственным профилем

**Правило:**  
Пользователь может **изменять только собственный профиль**, а не чужой.

**Реализация:**
```java
if (!profileId.equals(currentUserId)) {
    throw new ForbiddenException("Cannot edit other user's profile");
}
```

**Обоснование:** Приватность и безопасность. User A не может изменить профиль User B.

## ✅ Критерии успеха учебного проекта

Проект считается **успешно реализующим бизнес-идею**, если пользователь может выполнить этот **User Journey** полностью:

### Happy Path (Идеальный сценарий)

```
1️⃣ РЕГИСТРАЦИЯ
   └─ Пользователь регистрируется с email и паролем
      Status: ✅ Аккаунт создан, можно войти

2️⃣ АВТОРИЗАЦИЯ
   └─ Пользователь логинится и получает доступ
      Status: ✅ Авторизован, видит главное меню

3️⃣ ЗАПОЛНЕНИЕ ПРОФИЛЯ
   └─ Вводит имя, описание, возраст, город
      Status: ✅ Основная информация заполнена

4️⃣ ДОБАВЛЕНИЕ ИНТЕРЕСОВ
   └─ Выбирает min 1 интерес из справочника
      Status: ✅ Интересы добавлены

5️⃣ УСТАНОВКА ПРЕДПОЧТЕНИЙ
   └─ Указывает возрастной диапазон, макс расстояние
      Status: ✅ Предпочтения сохранены

6️⃣ ПОЛУЧЕНИЕ РЕКОМЕНДАЦИЙ
   └─ Видит список потенциальных партнёров
      Status: ✅ Получены персонализированные рекомендации
      Метрика: ≥ 5 профилей в списке

7️⃣ ВЫРАЖЕНИЕ ИНТЕРЕСА
   └─ Нажимает Like на интересном профиле
      Status: ✅ Like сохранён
      Метрика: Min 2 Like от пользователя

8️⃣ ПОЛУЧЕНИЕ MATCH
   └─ Другой пользователь тоже ставит Like
   └─ Система создаёт Match
      Status: ✅ Match создан, оба уведомлены
      Метрика: Min 1 Match

9️⃣ ОТКРЫТИЕ ЧАТА
   └─ Видит новый Match в списке
   └─ Открывает чат с пользователем
      Status: ✅ Чат доступен

🔟 ОТПРАВКА СООБЩЕНИЯ
   └─ Пишет первое сообщение
      Status: ✅ Сообщение отправлено и доставлено
      Метрика: Ответ получен от другого пользователя

✅ SUCCESS
   User successfully found interesting person and initiated conversation!
```
