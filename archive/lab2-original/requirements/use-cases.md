# Nexus — Use Cases и варианты использования

**Use Cases (UC)** — детальное описание всех основных и альтернативных сценариев взаимодействия акторов с системой Nexus. Документ определяет функциональные требования, бизнес-правила, предусловия и результаты для каждого сценария.

---

## 👥 Акторы системы

| Актор | Описание |
|-------|---------|
| **Гость** | Неавторизованный посетитель, может регистрироваться и авторизоваться |
| **Пользователь** | Авторизованный пользователь Nexus с заполненным профилем |
| **Система рекомендаций** | Внутренний компонент backend, рассчитывающий совместимость |

---

## 🔐 UC-01. Регистрация

**Актор:** Гость  
**Предусловие:** Email ещё не используется в системе.

### Основной сценарий
1. Гость открывает форму регистрации
2. Вводит email и пароль
3. Frontend отправляет данные на backend
4. Backend валидирует данные (формат, правила пароля)
5. Backend создаёт новый User
6. Пользователь получает успешный ответ
7. Может авторизоваться в системе

### ❌ Негативные сценарии
- Email уже зарегистрирован в системе
- Email имеет неверный формат
- Пароль не соответствует правилам (слишком короткий, слабый)
- Отсутствует обязательное поле (email или пароль)

**Результат:** ✅ Создана учётная запись, пользователь может войти

---

## 🔑 UC-02. Авторизация

**Актор:** Гость  
**Предусловие:** Пользователь зарегистрирован в системе.

### Основной сценарий
1. Пользователь вводит email и пароль на форме входа
2. Backend проверяет учётные данные в БД
3. Проверяется соответствие пароля (хеш)
4. При успехе backend генерирует JWT токен
5. Frontend сохраняет сессию (токен)
6. Frontend открывает основное приложение

### ❌ Негативные сценарии
- Неверный email или пароль
- Пользователь деактивирован/заблокирован
- Отсутствуют обязательные поля (email, пароль)
- Множественные неудачные попытки входа

**Результат:** ✅ Пользователь авторизован, имеет доступ к функциям

---

## 👤 UC-03. Заполнение профиля

**Актор:** Пользователь  
**Предусловие:** Пользователь авторизован в системе.

### Основной сценарий
1. Пользователь открывает редактор профиля
2. Вводит личные данные (имя, описание, фото)
3. Добавляет список интересов (выбор из предопределённого набора)
4. Устанавливает предпочтения (диапазон возраста, местоположение и т.д.)
5. Сохраняет изменения
6. Система валидирует и сохраняет данные в БД
7. Профиль становится доступным для рекомендаций

### ❌ Негативные сценарии
- Описание профиля превышает допустимую длину
- Выбран несуществующий Interest
- Попытка добавить один Interest дважды (дубликат)
- Попытка изменить чужой профиль (доступ запрещён)
- Фото имеет неподходящий формат или размер

**Результат:** ✅ Профиль готов и включен в систему рекомендаций

## 💡 UC-04. Получение рекомендаций

**Актор:** Пользователь  
**Внутренний участник:** Система рекомендаций (сервис расчёта score)  
**Предусловия:**
- Пользователь авторизован
- Профиль заполнен и активен

### Основной сценарий
1. Пользователь открывает экран рекомендаций
2. Frontend отправляет запрос на backend
3. Backend получает профиль, интересы и предпочтения текущего пользователя
4. Исключает самого пользователя из списка кандидатов
5. Исключает недоступные профили (неполные, заблокированные)
6. Учитывает историю предыдущих взаимодействий (уже лайкнутые, скипнутые)
7. **Система рекомендаций** рассчитывает score совместимости каждого кандидата
8. Сортирует кандидатов по убыванию score
9. Возвращает отсортированный набор рекомендаций
10. Frontend отображает карточки профилей (на основе рекомендаций)

### ❌ Негативные сценарии
- Профиль пользователя заполнен недостаточно (отсутствуют интересы)
- Подходящие кандидаты отсутствуют (все уже обработаны или не подходят по фильтрам)
- Сервис расчёта рекомендаций завершился ошибкой (исключение, timeout)
- Backend временно недоступен

**Результат:** ✅ Пользователь получил релевантный список профилей либо корректное пустое состояние

## 👍 UC-05. Like пользователя

**Актор:** Пользователь  
**Предусловия:**
- Пользователь авторизован
- Целевой профиль существует и доступен
- Целевой профиль не принадлежит текущему пользователю

### Основной сценарий
1. Пользователь нажимает кнопку Like на карточке
2. Frontend отправляет запрос на backend (user_id, target_id)
3. Backend сохраняет положительную реакцию (Like) в БД
4. Backend проверяет наличие обратного Like (от целевого пользователя)
5. **Если обратный Like существует:**
    - Backend создаёт новый Match (двусторонняя связь)
    - Генерирует уведомления обоим участникам
    - Отправляет ответ "Match!"
6. **Если обратного Like нет:**
    - Отправляет ответ "Like сохранён"
7. Frontend обновляет интерфейс

### ❌ Негативные сценарии
- Like уже существует (попытка повторного лайка)
- Пользователь пытается поставить Like самому себе
- Целевой пользователь недоступен/деактивирован
- Целевой профиль был удалён

**Результат:** ✅ Реакция сохранена. При взаимности создан Match и отправлены уведомления

---

## ⏭️ UC-06. Skip рекомендации

**Актор:** Пользователь  
**Предусловие:** Пользователь просматривает рекомендации.

### Основной сценарий
1. Пользователь нажимает кнопку Skip на карточке
2. Frontend отправляет запрос на backend
3. Backend фиксирует обработку рекомендации (записывает в историю)
4. Карточка исчезает из текущего набора
5. Frontend запрашивает следующую рекомендацию
6. Следующий вызов API учитывает историю пропусков

### ❌ Негативные сценарии
- Рекомендация уже обработана ранее (Double-skip)
- Профиль недоступен/удалён
- Нет следующей рекомендации

**Результат:** ✅ Пропущенный профиль не появится в новых рекомендациях

## 📋 UC-07. Просмотр списка Match

**Актор:** Пользователь  
**Предусловие:** Пользователь авторизован.

### Основной сценарий
1. Пользователь открывает раздел "Совпадения" (Matches)
2. Frontend отправляет запрос на backend
3. Backend выбирает все Match, где пользователь является участником
4. Возвращает список профилей, с которыми есть взаимный Like
5. Frontend отображает список совпадений

### ❌ Негативные сценарии
- Match отсутствуют (нет взаимных лайков)
- Пользователь пытается запросить Match другого пользователя
- Один из участников Match был удалён

**Результат:** ✅ Отображён список доступных совпадений либо пустое состояние

## 💬 UC-08. Отправка сообщения

**Актор:** Пользователь  
**Предусловия:**
- Пользователь авторизован
- Существует Match между отправителем и получателем

### Основной сценарий
1. Пользователь открывает чат соответствующего Match
2. Вводит текст сообщения
3. Нажимает кнопку "Отправить"
4. Frontend отправляет сообщение на backend
5. Backend проверяет принадлежность пользователя к Match
6. Backend валидирует сообщение (не пустое, в пределах длины)
7. Backend сохраняет Message в БД (с timestamp)
8. Backend создаёт уведомление для второго участника
9. Сообщение появляется в истории обоих участников

### ❌ Негативные сценарии
- Match не существует
- Пользователь не является участником этого Match (попытка несанкционированного доступа)
- Сообщение пустое или содержит только пробелы
- Сообщение превышает допустимую длину (например, 5000 символов)
- Один из участников был заблокирован или удалён

**Результат:** ✅ Сообщение сохранено и доступно обоим участникам Match

## 📖 UC-09. Просмотр истории чата

**Актор:** Пользователь  
**Предусловие:** Пользователь авторизован и находится в чате Match.

### Основной сценарий
1. Пользователь открывает чат с другим участником
2. Frontend запрашивает историю сообщений у backend
3. Backend проверяет доступ пользователя к этому Match
4. Backend возвращает сообщения Match в хронологическом порядке (от старых к новым)
5. Включает информацию об отправителе и timestamp
6. Frontend отображает историю переписки

### ❌ Негативные сценарии
- Отсутствует доступ к Match (пользователь не является участником)
- Match не существует
- Нет сообщений в истории (пустой чат)
- Backend недоступен

**Результат:** ✅ История чата отображена, пустой чат показан корректно

## 🔔 UC-10. Работа с уведомлениями

**Актор:** Пользователь  
**Предусловие:** Пользователь авторизован.

### Основной сценарий
1. Пользователь открывает Центр уведомлений
2. Frontend запрашивает Notification текущего пользователя
3. Backend возвращает список уведомлений (отсортированные по времени, новые сверху)
4. Пользователь открывает или отмечает уведомление прочитанным
5. Frontend отправляет обновление статуса на backend
6. Backend обновляет поле `is_read` в БД
7. Интерфейс обновляется (уведомление помечается как прочитанное)

### ❌ Негативные сценарии
- Попытка изменить чужое уведомление (доступ запрещён)
- Уведомление не найдено
- Уведомление уже удалено
- Попытка одновременного обновления одного уведомления несколькими запросами

**Результат:** ✅ Уведомления отображены и могут быть помечены как прочитанные

## 🎯 Ключевые вопросы для защиты

### Почему нельзя писать без Match?
Это **бизнес-правило** ограничивает нежелательные сообщения и связывает чат с взаимным интересом. Гарантирует, что оба участника выразили интерес друг к другу перед началом общения.

### Что будет, если рекомендаций нет?
API возвращает **пустой список**, а frontend показывает соответствующее состояние (например, "Пока нет новых рекомендаций"). Это **не является серверной ошибкой** — это нормальное состояние.

### Что будет при повторном Like?
Backend должен **предотвратить создание дубля** на уровне бизнес-логики (проверка в коде) и на уровне БД (уникальное ограничение `UNIQUE (user_id, target_id)` на таблице Like). Вторая попытка вернёт ошибку или игнорируется.

### Как расширить алгоритм рекомендаций?
**Базовая формула score** находится в отдельном сервисе (`RecommendationService`). Можно заменить на ML-модель, не меняя API получения рекомендаций. Backend абстрагирует логику расчёта.

### Нужно ли удаление сообщений и Match?
На текущем этапе UC не предусматривают удаление. Можно расширить UC-08 и UC-07 для поддержки soft-delete (помечается как удалённое, но остаётся в истории).

### Как обеспечить безопасность доступа?
Каждый запрос проверяет:
- ✅ Пользователь авторизован (JWT токен валиден)
- ✅ Пользователь имеет право на данный ресурс (проверка user_id в Match, Message и т.д.)
- ✅ Данные валидны перед сохранением
